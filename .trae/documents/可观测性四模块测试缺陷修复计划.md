## 三、Proposed Changes

### 3.1 D-01 · Trace 多轮台账轮次优先 + 偏移分页

**文件**：`src/devprompt_ai/memory/trace_store.py`

- `query_events` 排序改为 `ORDER BY turn_index ASC, started_at ASC, trace_id ASC, seq ASC`（轮次优先，同轮按录制时间/链路稳定）。
- 分页游标从「seq 下界」改为「已读行偏移」：
  - 删除 `seq > ?` 条件；
  - SQL 增加 `OFFSET ?`，参数 `max(0, query.cursor)`；
  - `next_cursor = query.cursor + len(kept)`（仅 `has_more` 时，否则 0）。
- `TraceQuery.cursor` 契约字段不变（前端一直把它当不透明整数），`tests/memory/test_trace_store.py`、`tests/api/test_obs_api.py` 现有的 `next_cursor == 1` 断言仍成立。
- `list_trace_events`（单 trace）保持 `ORDER BY seq ASC` 不变。

**为什么**：不改 API/OpenAPI 结构即可让轮次顺序成立并修复跨 trace 分页漏数据；`(turn_index, seq)` 复合游标需要改契约与前端，收益不足。

### 3.2 D-02 · 登记 trace.write_failed 并保证 emit 不二次抛错

**文件**：`src/devprompt_ai/observability/logging.py`、`src/devprompt_ai/harness/obs/trace_collector.py`

- `EVENT_NAMES` 增加 `"trace.write_failed"`。
- `TraceCollectorImpl.flush` 的 except 分支中，用 `try/except Exception` 包裹 `emit(...)`，仅 `logger.warning`，确保任何观测失败都不外抛（fail-open）。
- 保留 `logger.warning("trace.write_failed", exc_info=True)` 作为诊断日志。

### 3.3 D-03 · sync_alerts 使用 BEGIN IMMEDIATE 串行化

**文件**：`src/devprompt_ai/memory/metrics_alert_store.py`

- `sync_alerts._run` 中，`executescript(DDL)` 之后显式 `conn.execute("BEGIN IMMEDIATE")`，读-判-写全部在该写事务内完成，末尾 `conn.commit()`；异常路径由连接上下文回滚。
- 不修改 `metrics_alerts` 索引与表结构（避免迁移风险）。

**为什么**：`BEGIN IMMEDIATE` 立即取得 SQLite 写锁，三个并发 `evaluate` 变为串行，第二次起走 UPDATE 分支，不再触发唯一索引冲突；改动仅 2 行且对所有调用方透明。

### 3.4 D-04 · /runs 允许创建前端新会话

**文件**：`src/devprompt_ai/state.py`、`src/devprompt_ai/service.py`、`src/devprompt_ai/runtime/runs.py`

- `start_turn(store, user_id, session_id, *, create_missing: bool = False)`：
  - 会话不存在且 `create_missing=True` 时创建 `FlowSession(user_id, state=DONE, data={})` 后继续走「重置到 INIT」逻辑；
  - 默认 False，保持 `/optimize` 未知 session 仍返回 6003（契约不变）。
- `ForgeService.optimize` 增加关键字参数 `create_session: bool = False`，透传给 `start_turn`。
- `RunManager._execute` 调 `service.optimize(..., create_session=True)`。
- 仅 `/runs` 路径启用自动建会话；`/optimize`、`/optimize/stream` 行为不变。

**为什么**：前端在 `OptimizePage` 用 `crypto.randomUUID()` 生成 `session_id` 再 `POST /runs`，执行侧必须创建容器；放在 state 层可复用状态机与乐观锁，避免 RunManager 直接操作存储。

### 3.5 D-05 · 旧入口补齐 Session Log（用户已选「补齐事件写入」）

**文件**：`src/devprompt_ai/runtime/events.py`、`src/devprompt_ai/interfaces/api/routes.py`

新增 `BufferedEventSink(ProgressSink)`（放在 `runtime/events.py`，复用已有 `EventSink`）：

- 缓冲 `ProgressEvent`（新会话在 `optimize` 返回前不知道 `session_id`）；
- `start(session_id)`：先写 `run.started`（`run_id`/`request_id` 均为本次 `request_id`，与 Trace 的 `run_id` 对齐），再按序补写缓冲事件；
- `emit(event)`：有下游 sink 时先转发（`/optimize/stream` 的 SSE 帧不受影响）；已绑定则直接写 `run_events`，否则入缓冲；
- `finish(session_id, payload, *, status, state)`：绑定（如未绑定）、写 `snapshot` 与 `stop`；
- `fail(session_id, code, message)`：已绑定则写 `error`；
- 所有 bus 写入 try/except，观测失败只 `logger.warning`（fail-open）。

`routes.py`：

- 新增 `_event_log(request_id, downstream=None)`：延迟 import `runtime_routes._bundle` 取 `bundle.bus`（避免模块循环依赖）；取不到（如单测 Fake service 无 `.config`）返回 None，等于关闭日志。
- `post_optimize`：`progress=log`；异常写 `error` 后原样抛出；成功后 `finish(snapshot.session_id, snapshot payload, status, state)`。
- `post_optimize_stream`：在 producer 内构造 `log` 并作为 `progress=log or sink` 传入，终态写 `snapshot`/`stop`，异常写 `error` 后继续走原有 error 帧。

**为什么**：把事件写入收敛在 runtime 适配器，路由仍只做装配；不改变 `/optimize` 同步返回与 SSE 帧契约。

### 3.6 D-06 · token 用量改为「请求级聚合差值」

**文件**：`src/devprompt_ai/common/cost.py`、`src/devprompt_ai/harness/obs/traced_ports.py`

- `common/cost.py` 新增 `peek_llm_usage() -> Usage`（只读当前 ContextVar，不清零，区别于 `take_llm_usage`）。
- `TracedGenerator.generate_single` / `answer`：
  - 调用前记录 `before = peek_llm_usage().total`；
  - 调用后用 `_tokens(before)` 计算；
- `_tokens(before_total=0)`：优先返回 `peek_llm_usage().total - before_total`（>0 时），否则回退现有 `last_usage()["total_tokens"]`；全程异常按 0。

**为什么**：`common.cost` 聚合在真实运行中已被正确记录（`forge_turns.usage_json.llm_tokens=3825`），差值口径与 Metrics 的 token 统计同源；不再依赖 `last_usage` 的上下文传递细节，避免真实 LLM 下恒 0。生成/回答在同一请求内串行，差值不会误计其它调用。

### 3.7 D-07 · 回放比对按 (kind, name, call_key) 对齐

**文件**：`src/devprompt_ai/domain/obs/replay/compare.py`

`compare_streams` 改为两段式：

1. 有 `attributes.call_key` 的事件：按 `(kind, name, call_key)` 建右侧 FIFO 队列，遍历左侧按 key 取对应事件比较；缺右侧记 `missing=actual`，右侧多余记 `missing=expected`；
2. 无 `call_key` 的事件（`action.end` 等顺序节点）：仍按相对位置对齐。

输出节点顺序以左侧录制顺序为准，`seq`/`kind`/`name` 仍取实际事件，`match` 判定与 diff 逻辑不变。补充单测：左右两侧 `file.read`/`file.exists` 顺序互换时全部 match。

**为什么**：并发取证只影响完成顺序，不影响 `call_key` 与输出；按 key 对齐消除假 diverged，同时保留顺序节点的位置比较能力。

## 四、Assumptions & Decisions

- **D-05 已确认**：用户选择「补齐事件写入」，`/optimize` 与 `/optimize/stream` 均写 `run_events`；`/followup` 不在本次范围（报告只列 `/optimize`）。
- **D-08 不修代码**：余额/账号问题是外部依赖，报告中保留历史成功证据与复跑命令。
- **游标语义**：`cursor` 从「seq 下界」改为「行偏移」，不新增字段、不改前端；现有测试中的 `next_cursor == 1` 断言语义兼容。
- **不改 DDL**：D-03 只用 `BEGIN IMMEDIATE`，不动 `metrics_alerts` 索引，避免历史库迁移风险。
- **观测失败 fail-open**：新增的 Session Log 写入、token 采集、trace 写失败事件均不得影响业务返回。
- **不修改**：Session Log 的 `/events`、Metrics 规则阈值、Replay API、前端代码均不动。
