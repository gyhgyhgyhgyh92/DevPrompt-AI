# 输出模板升级：四段式结构化改造

> 目标：让 DevPrompt AI 的最终产出从「自由散文」升级为**四段式结构化提示词**，并补齐上游证据，使下面这条原句能产出你给的示例级结果。
>
> 原句：`将当前项目中的前端页面中的管理员界面中的新增图书按钮改为红色。`
>
> 你已选择：**全链路改造** + **A/B/C 全部档位统一四段式**。

### 2.2 检索词表缺口（关键）

`domain/retrieval/candidates.py` 的 `ZH_EN_MAP`（L50–403）现有：`新增→add`(L53)、`按钮→button`(L143)、`页面→page`(L217)、`修改→modify`(L56)、`样式→style`(L194)、`颜色→color`(L203)。

### 2.3 证据层缺口（关键）

`GenerationContext`（`domain/generate/ports.py:21`）只有 `facts_summary` —— 七项布尔 + ≤200 字符**单行**证据，**不含代码片段**。

`locate_symbol`（`locate.py:28`）虽然 `await reader.read()` 读了整份文件，但只提取 `selectors` / `tokens`，正文被丢弃。

→ 写不出「位于 `PageContainer` 的 `extra` 属性中」，也写不出「原代码 → 新代码」。

**且**：组件声明在 L55，按钮在 L233，相差 **178 行**。因此片段锚点**不能取 `definition_line`**。

### 2.4 模板层缺口

`common/i18n.py:81` 的 `template.body_semantics` 只要求「包含角色与目标、上下文、必须遵守的约束、期望的输出格式」——散文式，无段标题、无四段、无「原代码 → 新代码」。

### 2.5 Qoder 对照

Qoder 官方文档与博客把「一键增强提示词」拆成四维：

| 维度 | Qoder 做法 | DevPrompt AI 现状 |
|---|---|---|
| 需求明确化 | 模糊描述转具体任务 | `ASK` 动作 + 研判，已有 |
| 场景上下文化 | 工程结构 / 对话 / 相关上下文作额外输入 | **弱**（只有符号+七布尔） |
| 约束条件完善化 | 补充性能、边界、错误处理、安全、代码规范 | 部分（T-2/T-5/T-6 声明） |
| 结构化输出 | 「任务目标 / 输入输出 / 约束条件 / 示例参考」模块化 | **缺失** |

来源：[一键优化提示词](https://docs.qoder.com/zh/user-guide/context/optimize-prompt)、[Qoder 上线提示词增强功能](https://qoder.com/zh/blog/qoder-promt-enhancement)

本次改造对应第 2、4 两个缺口，第 3 个由既有 `prompt_guard.py` 承担。

## 三、改造方案

按依赖顺序三处。

### 改造 1 · 检索词表补全

**文件**：`src/devprompt_ai/domain/retrieval/candidates.py`，`ZH_EN_MAP`（L50–403）

**改动**：按现有分组插入以下条目

```python
"图书": "book",
"书籍": "book",
"管理员": "admin",
"界面": "ui interface",
"红色": "red danger",
"危险": "danger",
"主色": "primary",
"主题": "theme",
"令牌": "token",
```

**Why**：让「图书 / 管理员 / 红色 / 界面」桥接到 `book / admin / red|danger / ui|interface`。`BookListPage` 因此获得 `book` 命中（+2.0），总分从 4.0 升至 6.0；同时 `red` / `danger` 进入 BM25 与 RRF 的查询词。

**How**：纯数据追加。`expand_zh_en`（L406）只增词元不减，既有命中不受影响；`_emit` 已支持空格分隔的多词元（`"ui interface"`、`"red danger"`）。

**风险**：新增词元会改变同分 tie-break。**必须重跑 W1 召回率**（见 §六）。

## 四、假设与决策

| # | 决策 | 理由 |
|---|---|---|
| D1 | 代码片段只进 `GenerationContext`，不进 `facts_summary` | MUST-09 约束的是「候选 → 决策层 state」；生成层需要片段才能写出位置与 diff。分离后决策层 state 体积不变 |
| D2 | 片段锚点按原句在文件内定位，而非 `definition_line` | 实测相差 178 行，按定义行取片段拿不到按钮 |
| D3 | 设计令牌用一次 rg 探测，不解析项目文档 | 你选择「全链路」而非「全链路 + 规范注入」；`antdTheme.ts:10` 已含 `colorError`，足以支撑一致性检查 |
| D4 | 不改七项事实模型 | AntD 项目 `token_defined` 恒假导致封顶 B 档，属既有设计边界。扩大范围会牵动 `is_evidence_complete` / 交付门 / 档位判定，本次不动 |
| D5 | A/B/C 全档四段式 | 你明确选择；A 档靠 `template.sections.a` 降级，避免结构空转 |
| D6 | 片段上限 2400 字符 / 36 行 | 约 1k token；`_generate_variants_guarded` 已有超窗压缩重发兜底 |
| D7 | 纯回答模板不受影响 | 它的契约是「只回答、不产出方案」，四段式会让它越界 |

## 五、已知限制（本次不解决）

1. **C 档在 AntD 类项目仍不可达**：`token_defined` 搜的是 CSS 自定义属性 `--xxx`，AntD 用 JS 主题对象。要到 C 需扩展事实模型（D4 未做）。
2. **项目规范文档条款不进 prompt**：一致性检查只能引用代码内令牌，「UI 规范 6.1 节」这类文档条款不会被引用。
3. **片段锚点大小写**：用 `line.lower()` 匹配，纯大小写差异的标识符可能错配（如 `Add` vs `add`）——影响可控，片段仍是原文。
