## 一、Summary

对 2026-11-12/13 新增的 Session Log、Trace、Metrics、Replay 四个模块执行一次完整 E2E 集成测试，覆盖：

1. 四模块独立功能（采集、存储、查询、开关）。

## 二、Current State Analysis（基于代码探索）

### 2.1 模块实现现状

| 模块 | 数据源 | 存储 | API |
|---|---|---|---|
| Session Log | 运行时 `run_events`（仅 `POST /runs` 路径写入） | `SQLiteEventStore`（现有 runtime） | `GET /api/v1/events?session_id&before&limit`、`GET /sessions/{id}/stream` |
| Trace | `TraceCollectorImpl` 在 `ForgeService` 内采集 | `trace_events`（`memory/obs_schema.py`） | `/api/v1/obs/trace/*` 4 条只读路径 |
| Metrics | 对 `trace_events` 做投影聚合 | 聚合即时计算；告警落 `metrics_alerts` | `/api/v1/obs/metrics/{summary,alerts,config}` |
| Replay | 读取已存 Trace + 录制端口 dry-run | `replay_runs` / `replay_nodes` | `/api/v1/obs/replay/{runs,compare}` |

### 2.2 已核实的关键机制

- **跨模块连接键**：`POST /runs` 生成 `run_id`（运行时 UUID）并接收 `request_id`（`X-Request-ID` 或 UUID）。`run.started.data.request_id` = `service.optimize(request_id=...)` = Trace 事件 `run_id` / `turn.start.attributes.run_id`。这是四模块关联的主键。
- **Trace 采集**：`TraceCollectorImpl` 默认 `buffer_size=20`，`end_turn` 时 flush；写失败 fail-open 并标记 `partial`。
- **Trace 查询**：`SQLiteTraceStore.query_events` 当前 `ORDER BY seq ASC`，而 `seq` 是**每个 trace 从 1 开始**。多轮会话中跨 trace 的分页很可能错位/漏页——列为待验证的 P1 候选。
- **Session Log 数据源**：`POST /optimize` 使用内存 `_QueueSink`，不写 `run_events`；只有 `POST /runs` 经 `EventSink` 落库。因此 E2E 真实链路必须走 `/runs`。
- **Replay 确定性**：已具备 `normalize_decision_args`（剔除 `steps.duration_ms`）与 `reset_run_cache()`；真实 Trace 的 verify 尚未在真实 LLM 产物上验证。
- **真实 LLM 配置**：`~/.devprompt-ai/settings.json` 已配置 `deepseek-flash`（base_url=`https://api.deepseek.com`，有 key）。测试可读取该配置，但**绝不打印 key**。
- **可用测试夹具**：`eval/recall/mock-react-admin` 是现成小型 React 项目（`SubmitButton` + `--color-primary-500`），适合真实 LLM 跑短链路，不新增项目夹具。
- **测试基座**：`pytest` + `pytest-asyncio`（`asyncio_mode=auto`）、`httpx` 已具备；`tests/conftest.py` 默认禁用本地设置源，需在真实 LLM 用例中显式传配置。

### 2.3 静态探索发现的候选问题（待用例确认）

| 编号 | 候选问题 | 影响 | 初判 |
|---|---|---|---|
| C-1 | `query_events` 全局按 `seq` 排序，多轮 Trace 的 `seq` 重复 | Trace 事件台账多轮分页错位/重复/漏事件 | P1 |
| C-2 | Session Log 仅 `/runs` 写入，`/optimize` 无 run_events | 旧入口/直接调用看不到日志 | P2（行为差异，需文档化） |
| C-3 | 取消发生在 `turn.end` 前时 Trace 缺收尾事件 | Replay 对 partial Trace 只能 failed；Metrics 可能不评估 | P2 |
| C-4 | 高并发下 SQLite `BEGIN IMMEDIATE` 竞争 | 可能出现 `database is locked`，Trace 标 partial | P2 |
| C-5 | 真实 LLM 回放依赖录制 key 完全一致 | 真实产物 verify 可能 diverged | P1（需实测） |

### 3.2 新增报告运行器

`scripts/obs_e2e.py`（标准库 + httpx，零新依赖）：

1. **隔离启动真实服务**
   - 读取 `~/.devprompt-ai/settings.json` 的 `model_service`（只取 base_url/model/api_key/provider/api_mode；不打印 key）。
   - 在 `eval/obs/runs/<timestamp>/` 生成临时 `settings.json`（仅 `model_service` 段）与临时 DB。
   - 环境变量：`DEVPROMPT_SETTINGS_FILE`、`DEVPROMPT_SETTINGS_DB`、`DB_PATH` 全部指向临时目录。
   - 用空闲端口启动 `uv run python -m devprompt_ai.main --host 127.0.0.1 --port <port>`，轮询 `/api/v1/health` 直至就绪（≤30s）。
   - 结束后 `terminate` → 等待 10s → `kill`；确保不触碰用户真实 DB。
2. **真实 LLM 场景（RL）**
   - RL-01 单轮成功：`POST /runs` → SSE `/sessions/{id}/stream?since=0` 至 `stop`；断言 `run.started`、thought/action、`snapshot`、`stop` 齐备。
   - RL-02 两轮会话：同一 `session_id` 第二次 `POST /runs`（句子沿用同一目标）；断言两条 Trace、`turn_index` 0/1、Session Log 两段 run、Metrics 会话聚合覆盖两轮。
   - RL-03 认证失败：用**另一个临时 DB + 无效 key** 启动第二个服务实例；`POST /runs` 后断言 `error` 事件、Trace `turn.end` failed、Metrics 错误率告警、Replay verify 以 failed 收尾（不崩溃）。
   - 真实调用预算：RL-01 1 次 + RL-02 1 次 + RL-03 1 次失败调用，共 3 次 `optimize`。
3. **确定性 pytest 执行**
   - 运行 `uv run pytest tests/e2e/obs -q -m "e2e and not real_llm"`，捕获汇总（passed/failed/xfail）。
4. **性能测量**
   - PF-01 采集延迟：`TraceCollectorImpl(buffer_size=1)` 写入 200 条单事件 + 200 批×20 条，记录 `record→flush→DB 可查` 的 P95。
   - PF-02 查询延迟：预置 5,000 条 `trace_events`（100 个 trace）+ 1,000 条 `run_events` 的临时 DB，启动服务后对 5 个端点各发 30 次请求，记录 P50/P95/Max。
   - PF-03 完整率：写入 10,000 条合成事件，按 `trace_id` 校验 `seq` 连续、行数一致、必需 kind 覆盖。
   - PF-04 长会话：50 轮 fake 运行，记录 DB 大小、Trace/Metrics 查询 P95（报告值，不设硬门槛）。
5. **报告输出**
   - `eval/obs/report-<YYYY-MM-DD>.md`：执行摘要、环境、用例矩阵、性能表、一致性证据、缺陷清单、风险评估、优化建议、复现命令。
   - `eval/obs/report-<YYYY-MM-DD>.json`：原始用例结果、耗时、P50/P95/Max、完整率、join 证据。
   - 控制台同时打印 PASS/FAIL 汇总；阈值不达标时退出码 1。

## 五、Assumptions & Decisions

1. **真实 LLM 范围**：RL-01 单轮 + RL-02 两轮 + RL-03 认证失败，共 3 次 `optimize`；目标项目用 `eval/recall/mock-react-admin`，句子用「把 SubmitButton 的主色改成 --color-primary-500」，第二轮「再给 SubmitButton 加一个 hover 状态」。
2. **缺陷仅报告**：确认缺陷以 `xfail(strict=True)` 留在套件中；不修改 `src/`。若缺陷导致测试无法继续，测试记录 `BLOCKED` 并说明，不绕过。
3. **Session Log 走 `/runs`**：这是唯一写 `run_events` 的链路；`/optimize` 的差异作为 C-2 报告项。
4. **性能口径**：采集延迟按「采集器写入并 flush 到 DB 可查」计；查询延迟按 HTTP API P95 计；完整率按「应为事件数 vs 实际可查行数」计。
5. **隔离与安全**：所有测试使用临时 DB/临时 settings；报告与日志不得出现 `sk-` 明文 key，脚本只读取、不打印。
6. **报告位置**：`eval/obs/report-2026-11-13.md` 与 `eval/obs/report-2026-11-13.json`；临时运行目录 `eval/obs/runs/<timestamp>/` 加入 `.gitignore`。
7. **不改前端**：四模块 UI 已有单元测试；本次 E2E 以 HTTP/API 与数据一致性为主，不新增浏览器自动化（现有前端测试已覆盖渲染）。
