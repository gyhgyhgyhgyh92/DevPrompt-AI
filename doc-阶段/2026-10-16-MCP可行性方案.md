# MCP 可行性方案（Batch 7 · N-10）

> 版本 v1.0 · 2026-10-16（**方案文档，不实施**）
> **定位**：评估「让 Claude Desktop 等 AI 客户端调用 DevPrompt AI 优化能力」的可行性。
> **结论前置**：本轮**不引入 `mcp` 依赖、不新增端点、不改契约**。落地与否需项目所有者裁定（理由见§3冲突登记）。

---

## 1. 前置条件核验（基于源码实测，非推测）

prompt-optimizer 的 mcp-server 只有 15 个 .ts 文件、约 200 行协议适配壳，其"零侵入"的前提是**能力本身已是纯函数**。核验本项目是否具备该前提：

### 1.1 能力形态：`ForgeService.optimize` **不是** `str → str`

```python
async def optimize(
    self, user_id: str, project_root: str, sentence: str, *, request_id: str
) -> FlowSnapshot
```

`FlowSnapshot` 携带 12 个字段（`session_id` / `status` / `state` / `questions` / `cleared` / `variants` / `ranking` / `target` / `facts` / `cost` / `message`）。而prompt-optimizer 的工具全部返回纯文本：

```
{"content": [{"type": "text", "text": <优化后>}]}
```

**差距**：结构化信息（尤其 `questions` 反问项与 `ranking` 推荐标记）在 MCP 纯文本通道里会被丢弃。prompt-optimizer 正是因此丢掉了全部结构化输出——**这是它的缺陷，不是可照抄的经验**。

### 1.2 多轮依赖：`optimize` **不是单次调用**

实测本项目存在三个相互依赖的调用：

| 调用 | 作用 | 依赖 |
|---|---|---|
| `optimize` | 检索+探针，可能返回 `status=ask` | 创建 session |
| `ask_followup` | 提交反问答复 → 继续 | 需要上一步的 `session_id` + `questions` |
| `escape` | 用户逃生「直接生成」 | 需要 `session_id` |

而 MCP 工具调用是**无状态的单次往返**。prompt-optimizer 的 `iterate-prompt` 把原prompt 同时当作 `originalPrompt` 和 `lastOptimizedPrompt`（`index.ts:316-322`），**等于放弃真实迭代链**——这是它为了适配 MCP 而做的能力降级。

**结论**：本项目的核心价值恰在**多轮澄清 + 信息完备度递进**（MUST-26 / MUST-28），这与 MCP 的单次无状态模型**直接冲突**。

### 1.3 请求上下文：MCP 无 HTTP 请求上下文

MCP 工具调用没有 `request_id`、没有用户身份、没有会话 Cookie。本项目：

- MUST-11 要求「涉及状态写入的接口必须带 `request_id` 以便追溯」
- `user_id` 恒为 `"local"`（本地单用户）

prompt-optimizer 的做法是硬编码 `modelKey: 'mcp-default'`（`index.ts:199/251/320`），**调用方无法选模型**。本项目若照做，会牺牲 F-604 的多模型注册表能力。

## 2. 可借鉴的两点（若未来实施）

### 2.1 工具描述三段式

```text
一句话定位（含 When-to-use）
  + Key capabilities（3-4 条祈使句）
  + Typical use cases（3 条「从 X 到 Y」）
```

且**多工具描述刻意互斥**（"Best for everyday chat" / "Best for custom assistants"），让 LLM 正确路由、避免选错工具。本项目若暴露 `search_symbols` / `generate_prompt` / `explain_fact` 三个工具，描述必须互斥。

### 2.2 schema 动态派生

prompt-optimizer 的 `enum` / `description` 从内部模板系统实时生成（`index.ts:71-78`），新增能力无需改 MCP 代码。本项目的档位（`level: "A"|"B"|"C"`）与反问类型本就是固定枚举，**收益低于它**——枚举不会动态扩展。

## 3. 冲突登记（实施前必须解决）

>⚠️ **新增 MCP 交付形态与宪法MUST-10「Web 单形态」直接冲突。**

MUST-10 原文：

> 本产品仅有 Web 一种交付形态（FastAPI HTTP API + 前端 UI），业务逻辑只允许存在一份。

增加 MCP 意味着：
- 交付形态从 1 种变2 种（虽共用同一 `ForgeService`，但入口、协议、错误处理各不相同）
- 需新增一条 delivery 形态的文档章节
- **必须修改 MUST-10 并标注 `BREAKING CHANGE:`**

此外还有两处次生影响：
- 打包形态：`pyproject.toml` 需新增 console script（与现有 `devprompt-ai` 并列）
- 契约：`openapi.json` 不变（MCP 不经 HTTP），但需新增 MCP 工具的入参 schema 定义

## 4. 反例清单（prompt-optimizer 的缺陷，不可照抄）

| 缺陷 | 位置 | 后果 |
|---|---|---|
| **CORS 全开** | `index.ts:405` `allowedOrigins:['*']` + `enableDnsRebindingProtection:false` | 任意站点可驱动本机 MCP 服务 |
| **内存字典会话** | `index.ts:385,404-406` | 多副本部署即失效；进程重启会话丢失 |
| **手写 `switch(name)` 分发** | `index.ts:159-340` | 工具一多就难维护，应改注册表 Map |
| **结构化信息丢弃** | `index.ts:204-209` | 统一降级为纯文本，丢失 questions / ranking |
| **三处重复的模型可用性检查** | `index.ts:185-194` 等 | 应提取为统一前置校验 |

## 5. 结论与建议

**结论**：本项目**具备技术可行性但不适合现在做**。

理由：
1. 能力形态不匹配（多轮 vs 单次）——这是**架构级冲突**，不是适配工作量的问题
2. 会牺牲项目最核心的差异化价值（MUST-26 自适应反问、MUST-28 信息完备度递进）
3. 需修改宪法MUST-10 并标 BREAKING CHANGE
4. 收益有限：真正的用户是 Web UI，而 Web UI **已经**提供了完整交互；MCP 的价值在于"让 AI 客户端调用"，但本项目的目标用户是人

**若未来确有需求，建议的最小路径**（不写代码，仅记录）：
1. 只暴露**单轮只读能力**（如 `explain_fact`：给定项目路径+组件名，返回七项取证结论）—— 该能力天然无状态、不触发反问、不需写入
2. 复用现有 `GET /project/scan` 的数据源，不新增 service 方法
3. MCP 层做适配，**不改 `ForgeService` 任何签名**（保持 MUST-10 的"业务逻辑只一份"）

**落地条件**：出现「希望 Claude Desktop 等客户端直接查询本项目代码事实」的真实需求时重启评估。
