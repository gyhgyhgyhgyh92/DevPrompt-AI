## 零、范围声明

- 本路线图只有**两层**：**内核（已交付）→ 形态（部分交付）**。形态阶段是本路线图的**终点阶段**。
- **第三阶段（能力层：读改码 + 跑验证）已取消**——理由见 §四。
- **不做 Plan 先行**：没有计划产物、没有确认门、没有 Ask/Craft/Plan 三模式 UI。
  「本轮目标由运行时持有」保留为**纯内部状态**（`TurnAnchor`），用户不可见、无额外交互。
- **不做桌面端**：不建目录、不做设计。
- 保留 Web 单形态、四层依赖单向、状态机唯一实现、不新增第三方依赖。

## 一、调研结论：七条可借鉴理念与两个必须避开的反例

| # | 参照做法 | 真实位置 | 本项目落点 |
|---|---|---|---|
| 1 | 目标由运行时持有，作为对抗摘要漂移的可信基准，压缩后在消息尾部重注入 | `src/context/task-contract.ts:11-35`、`compaction-controller.ts:1020-1032` | `domain/agent/anchor.py`（TurnAnchor：抽取 / 追加合并 / 渲染 / 反序列化） |
| 2 | 提交 / 验证 / 审查三者分离，门禁只读证据不产出证据 | `deliver-task.ts:122`、`tools/review-changes.ts:83` | `domain/delivery/gate.py`：只读 facts + claim_report，不重新取证 |
| 3 | 外环监督独立于内环，五阶段 hook，超时只丢自己产出 | `runtime-hooks.ts:265`、`create-runtime-hooks.ts:344` | `domain/hooks/`：3 阶段扩到 5 阶段，`allow/correct/halt` 三态 |
| 4 | 状态感知是纯函数、不调 LLM，输入全部来自已有信号 | `sensorium.ts:321,99-121` | `domain/agent/sensorium.py`：六维，全部取现有信号 |
| 5 | 收敛触发是「注入 + 标记 + 节流」，硬中止需低分 + 下降 + 已警告未采纳 | `convergence-detector.ts:982,1254` | 现有三判据**不动**；六维先 shadow 观测 |
| 6 | 证据不足分级披露，不一律拦截 | `obligation-tracker.ts:158-167`、`turn-orchestrator.ts:1519-1549` | 交付门只降质量标记，**不阻断交付** |
| 7 | 模式即权限（Ask / Craft / Plan） | CodeBuddy Plan Mode | **不采纳**：用户明确不要 Plan；本项目无写入能力，模式分级无收益 |

**必须避开的两个反例**

1. 天枢的 RED 状态**不阻断 git commit**，只披露（`deliver-task.ts:217-219` 注释明写「台账状态仅用于披露，
   不驱动任何门禁」）。本项目更不应阻断交付——阻断会让零基础用户拿不到任何东西。
2. 天枢 `claim-audit.ts:125` 实现了「宣称全绿但零验证则 block」，但**生产代码无调用点**（仅测试引用）。
   本次同类校验全部**接线并配测试**，不写死代码。

**调研后决定不做：前缀缓存分层**

天枢的 99.3% 缓存命中来自「多轮工具循环每轮重发完整对话历史」。本项目的 `chat_structured` 每次是
**独立单轮调用**，只有 system + user 两条消息——system 本身已稳定、天然命中，user 每次都变、无法缓存。
做 frozen/delta 分层无收益，只增复杂度。本阶段只加**缓存命中观测**
（读 `usage.prompt_tokens_details.cached_tokens`，缺失记 `None` 不虚报）。

## 三、第二阶段 · 形态（对话式）—— **本路线图的终点阶段**

目标：从「提交一次、返回三套卡片」变为连续对话流——每轮动作可视化、可中断、可回滚、可继续。

**已交付（本轮）**

1. **可中断**：生成中 composer 不再整块隐藏，改为禁用输入 + 显式「停止生成」；
   请求真取消 → 后端 `CancelledError` → `_abort_quietly` → ABORTED。
2. **以基线轮继续**：轮级操作条「以此轮继续」→ `POST /optimize` 带 `base_turn_id`，
   后端以该轮的取证与方案为起点新开一轮（**历史轮一条不少**，turn 表 append-only）。
3. **分页增量加载**：轮次「加载更早」、会话「加载更多」，取代 20 轮 / 50 会话硬顶。
4. **正文常驻**：历史轮正文进 store，切页面 / 折叠都不再丢，重复展开零请求。
5. **门禁卡片**：`DeliveryVerdict` 直接渲染，色阶用后端 `tone`，文案用后端 `disclosure`（前端零判定）。
6. **动作序列回看**：`agent_steps` 随摘要落库，历史轮可回看「这一步在做什么」。

**待办（形态阶段收尾）**

- 对话流整体布局与滚动策略（当前仍是旧版单轮 + 历史列表拼装）
- 「回滚」的完整语义（当前只做了「以基线轮继续」，尚未覆盖「撤销到某轮后丢弃后续轮」）
- 中断后的状态校对（中断后拉一次 `GET /result` 校对，界面不留残留 loading）

## 四、第三阶段 · 能力（读改码 + 跑验证）——**已取消**

**状态**：2026-11-05 由项目所有者决定取消。本节仅保留取消理由与重启前置条件，**不含实现计划**。

### 取消理由

1. **能力层会让本工具自身成为 Agent**，而产品的核心价值主张是「帮零基础用户把自然语言转成工程化语言，
   **提升下游 Agent 准确性**、减少幻觉」。一旦本工具自己改代码，「下游 Agent」就变成了「本工具自己」——
   原来靠三套方案 + 推荐标记交付的「诚实推荐」失去对象，MUST-27 的标记机制退化为**自评**。
2. **这是产品定位变更，不是技术升级**。形态阶段做完，本工具仍是「帮用户写出更好的提示词给别的 Agent 用」；
   若再推进能力层，它自己就变成了那个 Agent。两者是不同产品，不能共用同一套验收标准与错误责任口径。
3. **与 CodeBuddy / Trae 正面重叠**。写权限边界、沙箱、项目信任门、可中断执行——这些都是通用编码 Agent
   的标配，做出来也只是一套更小的同类品，投入产出比不划算。

### 若将来重启，必须先裁定四件事

| # | 待裁定项 | 为什么必须先定 |
|---|---|---|
| 1 | **执行边界**：只产出 patch 让用户确认，还是直接写盘？是否允许跑测试命令？ | 决定写权限、沙箱、审计三块的范围 |
| 2 | **责任归属**：执行失败（测试挂、构建断）时回滚、静默披露，还是交用户裁决？ | 对应天枢的 `deliver_task` 门禁与 `honest_blocked` 三态 |
| 3 | **是否保留 A/B/C 三套**：能改代码后还要不要三档？ | 极可能退化为「一版方案 + 执行前预览」，会牵动 MUST-28 |
| 4 | **与形态阶段的先后顺序** | 能力层要求对话流先就位，否则「中断 / 回滚」无处安放——建议形态阶段先行 |

### 第一阶段已就位、可复用的两处衔接点

结构不变，只换输入源，重启时无需改接口：

1. `DeliveryVerdict` 的 RED 判定可从「claims 未覆盖」扩展为「owned 改动未验证」，**字段结构不变**。
2. Sensorium 的「验证覆盖」维度可从 claims 覆盖率切换为「已验证改动 / 总改动」，**函数签名不变**。
