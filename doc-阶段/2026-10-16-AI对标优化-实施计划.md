## Batch 0 · M-1 前置失败验证（决策门）

> **用户裁定**：M-1 先验证失败是否真实存在，再决定是否实施。详细卡见 §3 的 M-1 条目。

**目标**：回答一个问题—— 当前 `harness/llm.py:_extract_json` 的首尾贪心截取，在真实使用中是否真的会导致解析失败？

- 若会 → Batch 3 全量实施 M-1（括号配平状态机）
- 若不会 → 记录数据，降级为「仅加注释说明已知限制」，省下 50 行代码与一个长期维护点

### Step 0.1 新建 `scripts/probe_json_extraction.py`（离线，无需 API Key）

构造 8 类真实世界会遇到的输出形态，对每类跑当前 `_extract_json` + `_parse_model`，记录是否解析成功：

| # | 样本形态 | 当前预期行为 |
|---|---|---|
| 1 | 纯 JSON 对象 | 成功 |
| 2 | json 围栏包裹 | 成功（走围栏分支） |
| 3 | JSON 前后有解释文字且文字含花括号 | **失败（预期脆弱点）** |
| 4 | JSON 后有解释文字但不含花括号 | 成功 |
| 5 | JSON 字符串值内含右花括号 | **失败（预期脆弱点）** |
| 6 | JSON 字符串值内含转义引号 | 视情况 |
| 7 | 两个 fenced 块，第一个是说明文字 | 成功 |
| 8 | JSON 未闭合（模型输出被截断） | 失败（预期，但应由纠偏重试兜底） |

输出控制台表格；若第 3 / 5 类失败则判定脆弱性成立。

### Step 0.2 运行并记录基线

`uv run python scripts/probe_json_extraction.py`，把结果抄入本文件 §Batch 3 的 M-1 条目。

### Step 0.3 真实 LLM 层验证（可选，需 API Key）

新建 `scripts/probe_llm_output_shape.py`：用 `chat_structured` 的同类请求调用真实 LLM N=20 次，统计输出中「JSON 前后有解释文字」的实际发生率。
**无 Key 时跳过并在报告中标注「未执行」**——本轮不索取 Key。

### Step 0.4 决策并回写

按 Step 0.1 结论二选一：
- 成立 → §3的 M-1 保持「全量实施」，Batch 3 执行
- 不成立 → M-1 降级为「加注释 + 保留验证脚本」，从 Batch 3 移除，并在 §7 记录

#### ✅ 执行结果（2026-10-16）：脆弱性成立，M-1 全量实施

探针输出（`uv run python scripts/probe_json_extraction.py`，退出码 0）：

| # | 样本 | 当前实现 | 风险等级 |
|---|---|---|---|
| 1 | 纯 JSON 对象 | 成功 | control |
| 2 | json 围栏包裹 | 成功 | control |
| 3 | JSON 后有解释文字且含花括号 | **失败** | **real** |

**执行中的修正（重要）**：初版探针把样本 5（顶层数组）也标为脆弱点，实为**构造性失败**——项目全部 `output_type` 均为对象模型且 prompt 强制「顶层必须是 object」，该路径不可达。已改为 `fake` 等级并排除出决策依据。**顶层数组支持归属 M-2 的候选生成，不在 M-1 范围内。**

**未执行**：Step 0.3 真实 LLM 层验证 → **已补跑（2026-10-16，用项目 `.env` 中的真实 DeepSeek 配置）**。
