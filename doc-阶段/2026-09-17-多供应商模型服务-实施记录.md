## 2. 核心技术决策：按调用注入而非进程级全局开关

**问题**：`set_default_openai_api` 是模块级单例。Web 并发下按「当前 provider」反复设置会相互覆盖——A 请求设 responses、B 请求设 chat_completions，表现为随机 4xx。

**方案**：`harness.llm.build_model(cfg)` 每次调用按当前条目构造**新 Model 实例**传入 `Agent(model=...)`。每个 Agent 持有自己的形态，零共享可变状态。

**MUST-24b 实测依据**（非推断）：

| 核实项 | 结果 |
|---|---|
| `Agent.__init__` 的 `model` 参数 | `str \| Model \| None`，接受实例 |
| `OpenAIChatCompletionsModel` / `OpenAIResponsesModel` | 均 `(model, openai_client, ...)`，可直接构造 |
| 两者是否 `Model` 子类 | ✅ |
| `Model` 抽象方法 | 仅 2 个（`get_response` / `stream_response`） |
| `anthropic` PyPI | 1.15.0（requires_python>=3.10） |
| `google-genai` PyPI | 2.31.0（requires_python>=3.10） |

**验证**：`test_concurrent_build_has_no_cross_talk` —— 40 次并发交替构造，Responses 20 + Chat 20，无污染。

## 4. 测试抓到的 5 个真实缺陷

| 缺陷 | 后果 | 发现阶段 |
|---|---|---|
| `MessageOutputItem(agent=None)` | `TypeError: cannot create weak reference to 'NoneType'`——`ModelResponse.output` 应放裸 item | W3 |
| output item 缺 `status`/`annotations`/`logprobs` | pydantic 校验失败 | W3 |
| Gemini `functionCall.args` 是 dict | 未 `json.dumps` 会让 Runner 按 JSON 字符串解析而抛错 | W3 |
| `write_model_registry` 被调用两次 | 幂等不出错，但白写一次 IO | W7 |
| 前端硬编码 3 个 PROVIDERS | 后端有 24 个，用户根本选不到其余 21 个 | W8 |

另有两个**测试自身**的问题：fake 结构与实现不符（`_Ctx` 缺 `stream`）、断言笔误（`前后半` vs `前半后半`）。

## 5. 「诚实」口径的三处延续

承接前几轮「不支持就说不支持」的同一原则：

1. **provider 目录查不到的端点留空**（`yi` / `sensetime` / `xiaomi-mimo`），UI 明示「官方端点未登记，请自行查询文档填写」——不编造端点
2. **`force_params` 不下发就收紧**（上一轮）：`reasoning_effort` 改走 `extra_body` 真正生效，而非被静默丢弃
3. **无 Key 的准入项标「未经本地验证」**，不伪装可用；过半失败时提示先排查网络/端点而非归咎供应商能力

## 6. 明确不做

| 项 | 理由 |
|---|---|
| `max_context_length` 自动截断 | 截断检索证据会削弱召回率，直接触碰 MUST-25 硬门禁 |
| `verbosity` / `top_k` / `stop` / `seed` | 需 `extra_body` 接线，与已登记项同批 |
| 改 `probe_llm_output_shape.py` 口径 | 它是 M-1 降级的复活条件探针，改口径会破坏新旧数据可比性 |
| 内置模型目录 | D4 裁定 |
